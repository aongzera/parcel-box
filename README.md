## 3. Install the tools

You only need the tools for the part you're working on.

| You're working on | Install |
|---|---|
| STM32 firmware | [STM32CubeIDE](https://www.st.com/en/development-tools/stm32cubeide.html) (free; needs an ST account to download). It also brings the ARM compiler and the flasher if you want to build from a terminal with `make` (see section 7). |
| ESP32 firmware | [VS Code](https://code.visualstudio.com/) + the **PlatformIO IDE** extension. Antigravity also works, since it is based on VS Code. |
| Dashboard / Firebase | [Node.js LTS](https://nodejs.org/), then `npm install -g firebase-tools` |
| Running the PC tests | `gcc` and `make` (see section 7) |
| Watching serial output | Built into PlatformIO, or [PuTTY](https://www.putty.org/) / Tera Term |

### Why PlatformIO and not the Arduino IDE?

The ESP32 code **uses the Arduino framework**: the same `setup()`/`loop()`, `Serial`, `WiFi` and so on. We just build it with PlatformIO instead of the Arduino IDE, because:
- the board settings and exact library versions are saved in the repo (`esp32/platformio.ini`), so it builds the same way on every laptop;
- the Arduino IDE keeps those settings on each person's computer, which leads to "works on my machine" problems.

So the code will look familiar if you know Arduino. Only the buttons are different (see section 5).

## 4. Working on the STM32 (STM32CubeIDE)

`stm32/` is an **STM32CubeIDE project** (`parcel-box`) generated by STM32CubeMX from `stm32/parcel-box.ioc`. Open it in the IDE to edit, build, flash and debug, and open the `.ioc` to see and change the pins and clock. The same sources also build from a terminal with `make`, which is what CI uses.

| Path | What's in it |
|---|---|
| `stm32/parcel-box.ioc` | The CubeMX configuration: pins (with labels `LID_REED`, `PARCEL_IR`, `BUZZER`), both UARTs, the 100 MHz clock |
| `stm32/Core/` | The hardware adapter. CubeMX generates `main.c`, `stm32f4xx_hal_msp.c` and `stm32f4xx_it.c`; our code in them sits inside `USER CODE` blocks. `board.c` (sensor pin meanings) and `serial.c` (sending and mirroring lines) are our own files. |
| `stm32/BoxCore/` | The Box logic core and the UART line writer: pure C, tested on the PC (section 7). The IDE builds `BoxCore/Src`; `BoxCore/Tests` is excluded. |
| `stm32/Drivers/` | ST's HAL and CMSIS (STM32CubeF4 1.28.3), as copied by CubeMX |
| `stm32/Makefile` | The command-line and CI build of the same folders, into `stm32/build/` |

### Open the project

1. Open STM32CubeIDE and pick any workspace folder, e.g. `C:\stm32-workspace`. **Don't** pick the repo folder itself.
2. Go to **File → Import… → General → Existing Projects into Workspace → Next**.
3. For **Select root directory**, browse to `parcel-box/stm32`.
4. `parcel-box` appears in the list. **Untick "Copy projects into workspace"**, so you edit the files in the repo, then click **Finish**.
5. To see the pin view, double-click `parcel-box.ioc` in the Project Explorer.

### Build, flash and run in the IDE

1. Plug the Nucleo into your laptop with its USB cable.
2. **Build:** click the 🔨 hammer button (or press `Ctrl+B`). `Debug` is the default configuration; `Release` is optimised for size. The output is `stm32/Debug/parcel-box.elf`.
3. **Flash and run:** click the ▶ green Run button. The first time, accept the default "STM32 C/C++ Application" settings. If it asks to update the ST-LINK firmware, say yes.
4. **Debug:** click the 🐞 bug button to step through code and set breakpoints.

### ⚠️ The one rule for CubeIDE code

CubeMX regenerates `main.c`, `stm32f4xx_hal_msp.c`, `stm32f4xx_it.c` and the other generated files whenever someone changes the `.ioc` and generates code. **Anything written outside the `/* USER CODE BEGIN … */` … `/* USER CODE END … */` comments gets deleted.**
- In generated files, only write code between those comments.
- Better still, put new code in its own files (like `board.c` and `serial.c`), which CubeMX never touches.
- If you change pins in the `.ioc`, update [docs/pinmap.md](docs/pinmap.md) too, and keep the pin labels: `board.c` uses `LID_REED_Pin` and `PARCEL_IR_Pin`.
- After regenerating, check `git diff` before committing.

### Build and flash from a terminal (optional, and what CI does)

You need `make` (section 7) and `arm-none-eabi-gcc`. STM32CubeIDE already contains the compiler; it just isn't on your PATH. Either add its `bin` folder to PATH, or tell make where it is:

```bash
# Windows, with STM32CubeIDE 1.19.0 (the plugin folder name has a version in it; check yours)
make -C stm32 ARM_PREFIX=C:/ST/STM32CubeIDE_1.19.0/STM32CubeIDE/plugins/com.st.stm32cube.ide.mcu.externaltools.gnu-tools-for-stm32.13.3.rel1.win32_1.0.0.202411081344/tools/bin/arm-none-eabi-

# Ubuntu / WSL: sudo apt install gcc-arm-none-eabi libnewlib-arm-none-eabi make
make -C stm32
```

This writes `stm32/build/parcel-box.elf` (plus `.bin` and `.hex`) and prints how much flash and RAM it uses. `make -C stm32 clean` deletes it.

To flash, run `make -C stm32 flash`. It builds, writes the firmware over SWD with ST's `STM32_Programmer_CLI` and resets the board. That tool also comes with STM32CubeIDE; if it isn't on your PATH, add `PROGRAMMER=...`:

```bash
make -C stm32 flash ARM_PREFIX=<as above> PROGRAMMER=C:/ST/STM32CubeIDE_1.19.0/STM32CubeIDE/plugins/com.st.stm32cube.ide.mcu.externaltools.cubeprogrammer.win32_2.2.200.202503041107/tools/bin/STM32_Programmer_CLI.exe
```

`STM32_Programmer_CLI -l st-link` lists connected boards. If it says "No ST-Link detected", re-plug the cable.

### See the debug log

The STM32 prints every line it sends to the ESP32 over the USB cable too (see the [pin map](docs/pinmap.md)).
1. Find the COM port: Windows Device Manager → Ports → **STMicroelectronics STLink Virtual COM Port (COMx)**.
2. Open it at **115200** baud, 8N1, in PuTTY or Tera Term. In CubeIDE you can use **Window → Show View → Terminal**, then open a Serial terminal.
3. Press the black RESET button. You'll see a boot line starting with `#` (only on this port, never sent to the ESP32), then, about 2 s later (with the Lid closed; if it's open, the first STS comes once it closes and settles), the first `STS,...` line and a `BOOT` line (the start of a new session), then a heartbeat `STS` line every 5 s.
4. Open and close the Lid (move the magnet). You'll see lines like `STS,EMPTY,LID_OPEN`. Once the session is open (step 5), each Lid cycle also sends an Event, e.g. `EVT,1,OPENED_EMPTY`.
5. With no ESP32 wired, nothing ACKs, so the STM32 resends `BOOT` every 1 s and sends no `EVT` at all: Events wait in the outbox. After 8 Lid cycles the outbox is full, and from the 9th on you'll see `# Outbox full: dropped Event N` for each new one. To ACK by hand, connect a 3.3 V USB-serial adapter to USART1: D8 (PA9, TX) → adapter RX, D2 (PA10, RX) ← adapter TX, and a shared GND. Open the adapter's port at 115200 8N1 and type `ACK,0` and Enter. The debug log says `# Session open`, `BOOT` stops, and the oldest waiting Event (`EVT,<n>,...`; `n` is 1 unless the outbox was full and dropped earlier ones) is sent, then resent every 1 s until you type `ACK,<n>`, and so on. Or wire the ESP32, which ACKs by itself. The ST-LINK port above can't take ACKs: it only shows the mirror, and the STM32 never reads its input.

## 5. Working on the ESP32 (PlatformIO)

### Open the project

1. In VS Code, go to **File → Open Folder…** and choose `parcel-box/esp32`. Open that folder itself, not the repo root, so PlatformIO detects it.
2. Wait for PlatformIO to finish installing the toolchain the first time. It can take a few minutes, and the status bar shows progress.

### Set up your secrets (one-time)

The ESP32 needs the WiFi password, Firebase login and Telegram token. These are **never committed**, because the repo is public.

```bash
cp esp32/include/secrets.example.h esp32/include/secrets.h
```

Then fill in `secrets.h` with the real values. Ask the code owner for them privately. `secrets.h` is gitignored, so it won't be committed. If CI ever says a `secrets.h` was committed, tell the code owner immediately so the keys can be changed.

### Build, upload and monitor

The buttons are in the blue PlatformIO bar at the bottom of VS Code:

| Button | Does | Arduino IDE equivalent |
|---|---|---|
| ✓ | Build | Verify |
| → | Upload to the board | Upload |
| 🔌 | Serial monitor (115200) | Serial Monitor |

If the upload fails with "no serial port" or "failed to connect":
- Use a USB **data** cable; some cables only charge.
- Hold the **BOOT** button, press and release **RST**, then release **BOOT**. Then upload again.
- On Windows, the board may need a **CP210x** or **CH340** USB driver, depending on which USB chip your board has.

### Test the ESP32 without the STM32

You can pretend to be the STM32. Open the serial monitor and type protocol lines, e.g. `STS,OCCUPIED,LID_CLOSED` or `EVT,1,DELIVERED`, and watch the Dashboard and Telegram react. The line format is in [product.md](product.md#uart-protocol-the-contract-between-the-boards).

## 7. Running the PC tests

The Box logic is tested on your laptop, with no board needed:

```bash
make test
```

This builds the Box logic core and UART line writer (`stm32/BoxCore/`) with each test suite in `stm32/BoxCore/Tests/` (one program per `test_*.c`) using `gcc` into `build/`, then runs them all. Each test prints `ok` or `FAIL`, and the command fails if any test fails.

To get `gcc` and `make` on Windows, either:
- **WSL** (recommended): run `wsl --install` in PowerShell, restart, then `sudo apt install build-essential` inside Ubuntu; or
- **MSYS2:** install it, then `pacman -S mingw-w64-ucrt-x86_64-gcc make`.

Skipping this is fine too: CI runs the same tests on every pull request.

## 8. How we work

1. **Pick a ticket** from [Issues](https://github.com/aongzera/parcel-box/issues). Only take one whose "blocked by" tickets are all closed.
   - `ready-for-agent`: coding work, normally done with Claude Code.
   - `ready-for-human`: hands-on or setup work. Follow the steps in the ticket.
2. **Make a branch:**
   ```bash
   git checkout -b 5-box-logic-core
   ```
3. **Do the work.** Use the words from [GLOSSARY.md](GLOSSARY.md) in code and commit messages.
4. **Commit and push:**
   ```bash
   git add -A
   git commit -m "Detect Delivery and Collection in the Box logic core"
   git push -u origin 5-box-logic-core
   ```
5. **Open a pull request** on GitHub and write `Closes #5` in the description. Wait for CI to go green ✅, then merge.

Never commit straight to `main`, and never commit `secrets.h`.

## 9. Troubleshooting

| Problem | Try |
|---|---|
| CubeIDE can't find the board | Re-plug the USB cable. Check Device Manager for "ST-Link". Update the ST-LINK firmware when CubeIDE offers. |
| My code vanished after generating code from the `.ioc` | It was outside `USER CODE` comments. Get it back with `git diff` or `git checkout -- <file>`. |
| `make -C stm32` says `arm-none-eabi-gcc: not found` | Pass `ARM_PREFIX=` pointing at STM32CubeIDE's compiler (section 4). |
| A sensor reads the wrong way round (e.g. Lid open shows `LID_CLOSED`) | Your KY module is inverted. Flip `LID_OPEN_LEVEL` or `PARCEL_PRESENT_LEVEL` in `stm32/Core/Src/board.c`. |
| Nothing arrives on the ESP32 from the STM32 | Swap the TX/RX wires. Check that both boards share **GND**. Check both are set to 115200 baud. |
| IR sensor never detects the parcel | Turn its potentiometer. Check the EN jumper is on. Try a lighter-coloured parcel. |
| `make: command not found` | See section 7, or just rely on CI. |
| PlatformIO doesn't show its buttons | You opened the repo root. Open the `esp32/` folder instead. |
